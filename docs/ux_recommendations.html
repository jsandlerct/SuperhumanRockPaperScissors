Executive Overview

Strengths, recurring patterns, and how to read this document.

What's Working Well

  • Cohesive SNES aesthetic applied consistently across all screens — feels like a real 16-bit game
  • Progressive disclosure via Jessie tutorial beats (T-01 through T-14) — features appear when needed, not all at once
  • Session persistence handles interrupts gracefully — players resume exactly where they left off
  • The two-column match layout (scoreboard + action) is fundamentally sound on desktop
  • Two-stage delete confirmation is exactly the right UX for permanent data destruction
  • Constants file architecture makes tuning easy — all play-feel levers in one place
  • Powerup overflow prompt is blocking and explicit — no silent data loss
⚠

Most critical gap: The passive skills panel is currently commented out in match.js. Players who buy MIND/MYSTIC/FORTUNE passive skills have no in-match reminder of what those skills do or what their current activation state is. This is a significant retention risk for new players who will forget what they purchased.

ℹ

Issues are rated Critical / High / Medium / Low and tagged Both / Mobile / Desktop. Critical issues should block release. High issues should be addressed before playtesting wider audiences. Medium and Low are polish.

Intro & Title Screens intro.js · title.js

The first impression. Sets the tone, can't be reskipped without a reload.

Medium Both

Intro plays on every page load — no returning-user awareness

Problem

Every app load begins with the full intro narration, even for players returning mid-session or from an accidental refresh. After 5+ sessions, the text crawl becomes an obstacle, not an experience.

Recommendation

Store a flag srps_meta.introSeen = true after the first complete playthrough. On subsequent loads, show only the title screen (skip intro) unless explicitly triggered from a menu. Add a "Replay Intro" option on the title screen for those who want to see it again.

Low Mobile

Skip button competes with content at 50% opacity

Problem

The skip button sits at bottom-right at 50% opacity and stays visible throughout the crawl. On mobile it's easy to accidentally tap during the reading experience, but also easy to miss when you actually want to skip.

Recommendation

Fade the skip button in after 2 seconds (so the atmosphere has a moment to land), then show it at 70% opacity. A simple setTimeout with a CSS opacity transition handles this. Label it SKIP ▶ rather than just "SKIP" to suggest forward motion.

Low Both

Title screen "press any key" duplicates intro end-state

Problem

Both the intro end state and the title screen show a blinking "PRESS ANY KEY" prompt. Players who skip the intro see it once; those who watch fully see it twice within seconds. The repetition devalues both moments.

Recommendation

Remove the cursor prompt from the intro end state — let the title screen own that beat. On the intro, simply auto-advance to the title after a 1.5s pause at the end of the crawl, so the transition feels like a cinematic cut rather than a UI prompt.

Login / Account Screen login.js

Account creation, selection, and password entry. First functional interaction.

High Mobile

Error messages persist indefinitely after failed login

Problem

When a wrong password is entered, a red error message appears below the input field. It does not clear when the player starts typing again — it stays until the next render cycle. On mobile, this means the error sits on screen alongside the corrected password attempt, creating doubt about whether the fix worked.

Recommendation

Add an input event listener on the password field that clears the error element's text on any keystroke. Also auto-clear with a 5-second setTimeout as a backup. This is a 3-line change but dramatically reduces friction.

Medium Both

No real-time validation on account creation form

Problem

Username and password rules (length, allowed characters) are only validated on submit. Players discover problems after they've already committed to the input, which feels punishing — especially on mobile where typing is slower.

Recommendation

Add a character counter below the username input: "12 / 16" in real time. Show a dim hint line: "Letters, numbers, and underscores only." Color the counter red when over limit. Validate on blur rather than on submit for password length. No form-submit error for these — just inline hints.

Low Both

Account list has no hover / focus state

Problem

Existing account rows highlight with a ▶ cursor on keyboard selection but have no hover state for mouse users. On desktop, it's not obvious rows are clickable until you try. On mobile, the tap target should be the full row width, not just the text.

Recommendation

Add cursor: pointer and a hover background of var(--snes-border) (matching the button hover style) to .account-row. Ensure the row's padding makes the tap target at least 44px tall on mobile. Add touch-action: manipulation to eliminate 300ms delay on iOS.

Character Creation characterCreate.js

Name entry and portrait selection. First moment of player identity investment.

High Mobile

Portrait grid lacks labels — players can't tell portraits apart without tapping each

Problem

The 50-portrait gallery shows images only. Portrait IDs (e.g., male_3) are visible in dev tools but not in the UI. On mobile, the grid is 5 columns of 60px images — distinguishing faces requires zooming in or tapping each to see the preview. With 50 options, this becomes tedious.

Recommendation

Add a simple gallery counter above the grid: "PORTRAIT 1–10 OF 50" with previous/next page arrows (show 10 per page on mobile, 25 on desktop). This eliminates infinite scroll and gives players a sense of progress. Alternatively, add a simple "M1" / "F3" label below each thumbnail in 8px pixel font — small but present.

Medium Both

Name input has no live character counter

Problem

The name field shows "UP TO 16 CHARS" as placeholder text, which disappears once typing starts. Players using long names discover the limit only when the error fires on submit.

Recommendation

Replace placeholder with a live counter below the field: 12 / 16. Turn red when at or over 16. This one change eliminates an entire class of submit errors. Also apply maxlength="16" on the HTML input element to prevent the error entirely at the browser level (then the counter is just friendly feedback, not a guard).

Low Both

Confirm button gives no transition feedback

Problem

Clicking "CONFIRM" immediately navigates away. On slower devices, there's a brief blank moment while the skill tree screen renders — it can look like nothing happened, causing double-taps.

Recommendation

Briefly flash the confirm button text to "SAVING…" for ~300ms before navigating. This is a CSS class swap + setTimeout. The visual feedback prevents confusion about whether the tap registered.

Skill Tree Screen skillTree.js · skillTreePanel.js

The most complex screen in the game. Pre-season and off-season allocation. Lock In gate.

🔴

This screen carries the highest UX risk in the game. It introduces all 15 skill nodes per tree with cascading purchase rules, refund mechanics, and season-specific restrictions. Players who misunderstand it will make irreversible (or nearly so) decisions. Every friction point here has downstream consequences.

Critical Both

Refund cascade is silent — players don't know child nodes will also be refunded

Problem

When a player refunds a node, all child/descendant nodes are automatically refunded too. This is the correct game rule, but the UI gives zero warning before it happens. A player who carefully built MIND.1 → MIND.1.1 → MIND.1.1.1, intending to just refund the root to try MYSTIC, will lose all three purchases simultaneously with no heads-up.

Recommendation

Before executing any refund that has downstream cascades, show a brief confirmation: "Refunding this node will also refund: Neural Pattern Rec. (+10 pts), Neural Scan (+15 pts). Refund all 3 for +30 pts?" with YES / CANCEL buttons. List the specific node names so it's unmistakably clear what will be lost. This confirmation should only appear when there are cascades — a leaf node refund proceeds immediately.

Critical Mobile

On mobile, the detail panel and tree canvas overlap — you can't see both simultaneously

Problem

The detail panel slides up from the bottom (bottom sheet pattern) covering ~60vh of the screen. If the selected node is at the bottom of the tree, it's now hidden under the panel. The player must close the panel to see the node, then re-open to read its description — a dead loop on every buy/inspect cycle.

Recommendation

Two options: (A) Reduce the detail panel to 40vh max on mobile and give it a handle for users to manually expand. This keeps the tree visible above. (B) Switch to a swipe-up modal that dimly overlays the tree (the tree is still visible at 30% opacity behind it). Option A is simpler. Also: auto-scroll the tree canvas so the selected node is always above the fold before the panel opens.

High Both

Pulsing "available" node animation runs indefinitely — creates visual noise

Problem

Available (purchasable but not yet bought) nodes pulse continuously with a 2-second animation cycle. While helpful for initial discovery, the animation never stops — a player who has been looking at the tree for 30 seconds is still watching 6–8 nodes blink simultaneously. It becomes background noise and can induce mild eye strain.

Recommendation

Run the pulse animation 3 times, then stop. CSS supports this with animation-iteration-count: 3; animation-fill-mode: forwards. After the 3rd cycle, the node stays at its resting state. Alternatively, trigger the animation only when the available set changes (e.g., after a purchase unlocks new nodes) — a brief pulse to say "new options available here," then silence.

High Both

Lock In button disabled state is too subtle — players tap it repeatedly

Problem

The Lock In button becomes disabled when conditions aren't met (no node purchased, or Season 2+ without second tree). Disabled state is opacity: 0.4 — a 60% dim. On a dark SNES-palette screen with many other dim elements, this is not visually distinct enough. Players tap it and wonder why nothing happens.

Recommendation

When disabled, change the button text to the reason: "BUY A NODE FIRST" or "CHOOSE A SECOND TREE". Also add a subtle shake animation (@keyframes shake) triggered on each failed tap — this is a classic SNES UX pattern that communicates "not valid" without an error message. The shake should be 3–4px for ~300ms.

High Mobile

L4 nodes have 6px font — illegible on mobile screens

Problem

L4 node names use Math.max(6, COL * 0.088) — as low as 6px in the Press Start 2P pixel font. Names like "Mental Mysticism" and "Adv. Neural Pattern Rec." at 6px require 20/20 vision and perfect lighting to parse on a mobile screen. Cost labels at Math.max(5, COL * 0.075) — potentially 5px — are essentially invisible.

Recommendation

Set a minimum of 8px for name and 7px for cost in Press Start 2P at all viewport widths. If names don't fit at that size, abbreviate them in the node box (e.g., "Adv. NPR") and show the full name in the detail panel only. The node box is a navigation target — players don't need to read the full name from it, just recognize it.

Medium Both

Unspent points confirmation modal uses different styling than other modals

Problem

The "You have unspent points — are you sure?" popup in skill tree uses a generic .content-card overlay, while the powerup inspect popup uses #pu-popup with its own distinct styling. Two different modal patterns for the same type of interaction breaks visual consistency.

Recommendation

Standardize all in-game popups/modals to use the #pu-popup structure and styling. The CSS and backdrop logic already exist — it's a matter of wiring the unspent-points confirm through that same system. One modal component, used everywhere.

Tournament Screen tournament.js

Bracket display, match entry, concurrent NPC results, and tier progression.

High Both

No opponent preview before entering a match — players can't prepare

Problem

"ENTER ARENA" immediately starts the match with no information about the upcoming opponent. Players with Neural Scan or powerup decisions to make before a match have no opportunity to think strategically. High-ELO opponents look identical to low-ELO ones in the bracket view.

Recommendation

Add a Match Preview card between bracket and match: show opponent portrait (large), name, ELO, and a single-line strategy hint from Jessie (e.g., "They favor Rock in tournament finals." — generic enough to not require real data). Two buttons: ENTER ARENA and ▼ VIEW BRACKET. This also gives players a moment to activate any pre-match powerups if that mechanic exists.

High Mobile

Horizontal bracket scroll has no visual affordance on mobile

Problem

The bracket path and full bracket views use horizontal scrolling containers. On mobile, there's no shadow gradient or arrow indicator to tell players more content exists off-screen. T4 and T5 brackets (6+ rounds) frequently clip without any visual cue that scrolling is possible.

Recommendation

Add a CSS right-edge fade overlay to horizontally scrollable containers: background: linear-gradient(to right, transparent 80%, var(--snes-black) 100%) positioned absolutely at the right edge. This is the standard affordance for "more content to the right." Disappears when scrolled to the end. No JS required — pure CSS.

Medium Both

"Meanwhile…" NPC results panel timing is unclear

Problem

After the player wins a match, NPC vs NPC results appear in a panel. It's not immediately obvious these results are simulated simultaneously (not after the player's match) or whether the player is expected to read them vs. just click through.

Recommendation

Add a header: "⚡ HAPPENING NOW — WHILE YOU COMPETED" and show results appearing one at a time with a 400ms stagger animation. This reinforces the "concurrent matches" fiction and makes the panel feel alive rather than like a data dump. Continue button stays; players can skip by tapping it anytime.

Low Both

Pending bracket slots don't distinguish "opponent TBD" from "upcoming match"

Problem

Unplayed slots show ? regardless of whether the opponent hasn't been decided yet vs. the player hasn't played their path match yet. The ? state is ambiguous.

Recommendation

Three distinct slot states: (1) ? — opponent unknown (pre-round), with dim styling; (2) assigned portrait + name in dim/grayscale — opponent known, match pending; (3) full color — match played. State 2 uses the same portrait and name display as State 3 but at 40% opacity, giving players something to look at while making the pending state visually distinct.

Match Screen match.js

The core game loop. Most complex screen, most time spent here.

🔴

The match screen carries the most critical UX issues in the game. Players spend the majority of their play session here. Complexity is high by design, but several issues significantly raise the cognitive load beyond what the SNES aesthetic can offset with style.

Critical Both

Passive skills panel is commented out — players have no in-match skill reference

Problem

The renderPassiveSkillsPanel() call is commented out in the match render function. Players who purchased passive skills (Desperate Clarity, Third Time's the Charm, Lucky Socks, NPR, etc.) have no way to see their current activation state, cooldowns, or effect descriptions during a match. New players will forget what they bought within 2–3 rounds.

Recommendation

Uncomment and enable the passive skills panel immediately. If the rendering was commented out due to layout space constraints, collapse it behind a tap-to-expand ▶ PASSIVE SKILLS (3) toggle. The number badge shows count without requiring screen space. This is the single most impactful UX fix available.

Critical Mobile

Right panel content overflows without scroll affordance on mobile

Problem

The right panel during "picking" phase stacks: round indicator + active effects banner + NPR indicator + active skills + throw buttons + powerup tray + footnote. With 3 active skills and a 5-slot powerup tray, this exceeds viewport height on most phones. There's no visual scroll indicator, and the powerup tray at the bottom is easily missed.

Recommendation

Convert the right panel to a collapsible section layout:

  • Throw buttons — always visible, pinned to bottom of viewport on mobile
  • Active Skills — collapsible, default open (shows skill buttons)
  • Passive Skills — collapsible, default closed (shows count badge when closed)
  • Powerup Tray — collapsible, default open (shows powerup slots)
Collapsing is tap-to-toggle. Section headers show the count of items inside when collapsed. On desktop, all sections are open by default. This scales to any number of skills/powerups.

Critical Both

Powerup USE button doesn't show readiness state before opening popup

Problem

Players must tap a powerup in the tray to open the popup, then read the description, then find the USE button, then discover it's disabled with a reason. This 4-step flow for a dead end is especially frustrating when a powerup has a scope restriction (e.g., "tournament-scope: already active" or "must be used in gut check"). The player had no way to know before tapping.

Recommendation

Add a small visual state indicator to each powerup tray slot: a green ● dot if usable now, an amber ○ if restricted by phase (gut check only), and a red ✕ or dim border if already active/expired. This communicates usability at a glance without opening the popup. The popup itself should also lead with a bold status line: READY TO USE or CANNOT USE: tournament effect already active.

High Both

Active skill cooldown display is low-contrast and hard to read quickly

Problem

Skill button backgrounds use a dark-to-darker gradient to show cooldown remaining. The cdPips() function renders 3r ■■■□□ in small text below the skill name. During a match, players need to glance quickly at whether a skill is ready — the current display requires careful reading rather than a fast scan.

Recommendation

Replace the gradient background with a left-to-right colored fill indicator: green fill for the "ready" portion of the button background, draining as cooldown increases. The button text stays white on top. This is the same pattern used in MMO action bars and communicates readiness in under 100ms. Add a large centered READY label (in green) when cooldown is 0, replacing the pip display.

High Mobile

Gut check phase stacks multiple information panels with no clear hierarchy

Problem

During gut check with multiple powerup effects active (e.g., Schrödinger's Amulet + A Word From Your Coach + Espresso Shot + Lucky Penny), the phase renders 4+ separate information panels above the throw-change buttons. On mobile, these stack vertically and require significant scrolling. It's unclear which panel demands action vs. which is informational only.

Recommendation

Separate "requires action" panels (Lucky Penny coin flip, Espresso Shot backup throw) from "informational" panels (strategy reads, Coach hint). Required-action panels appear at top with a yellow border. Informational panels collapse into a single 📋 INTEL (2 reads) expandable below. Reduces visible complexity from 4 panels to 2 zones.

High Both

Overflow prompt's "new drop" and "existing powerup" cards are visually indistinct

Problem

The inventory overflow prompt shows the new drop alongside existing inventory slots, all with the same card styling and REPLACE buttons. Players can confuse which card is the "new" one they just earned and which are their existing powerups. This causes mis-replacements.

Recommendation

Give the new drop a distinct header panel with a yellow border and label "⭐ NEW POWERUP EARNED" above it. Existing powerups are listed below under a separator "— YOUR INVENTORY —". REPLACE buttons on existing powerups use red text. DISCARD button on the new drop is styled dimly — it's the option the player should use last. Add a "KEEP NEW → REPLACE OLD" mental model through layout order.

Medium Both

NPR accumulation indicator lacks an intuitive progress metaphor

Problem

NPR (Neural Pattern Recognition) shows as a percentage (e.g., NPR: 40%) in a text display. This communicates the value but not the urgency or the threshold. New players don't know if 40% is "almost there" or "barely started."

Recommendation

Replace text with a horizontal progress bar labeled "NEURAL SCAN" with segments marking 0%, 30%, 60%, 90% (the fire threshold). Bar fills blue-to-purple as it approaches 90%. Add a subtle glow and pulse at 80%+ to signal "approaching fire." This makes the mechanic immediately legible even on first encounter and creates anticipation.

Medium Both

Match history panel doesn't distinguish tie rounds from unplayed rounds

Problem

The round history tally uses icons for Win/Loss but tie rounds (which are common early-game) may not be visually distinct from an empty slot. Players counting their wins can misread their own score.

Recommendation

Three explicit states per history slot: W (green, filled), L (red, filled), = (gray, filled — tie), and ○ (dim border, empty — not played). The tie state is important because it tells the player "a round happened, just with no winner." Use the same pixel font and SNES palette — this fits the aesthetic and is readable at small sizes.

Tournament Summary summary.js

Post-match and post-season results. Trophy reveals, Jessie dialogue, milestone celebrations.

High Both

No ELO delta shown — players can't tell if they improved

Problem

The summary shows current ELO and world rank, but no change from the previous tournament. A player who went from ELO 1200 to 1240 sees "1240" — a number with no context. ELO systems only feel meaningful when the change is explicit.

Recommendation

Show: ELO: 1,240 ▲ +40 and RANK: #45 ▲ from #52. If rank declined: ▼ from #38. Store eloAtTournamentStart and rankAtTournamentStart in _tournament before the match begins so the delta is available on the summary screen. This is one of the highest-value feedback improvements possible — it closes the "did I do well?" loop that keeps players engaged.

High Both

Jessie dialogue fires on top of a summary screen the player hasn't read yet

Problem

Milestone and consolation dialogues trigger immediately when the summary screen loads, blocking the results view. Players who earned a trophy or rank milestone have to dismiss Jessie before they can see what they achieved. The dialogue interrupts the reward loop rather than extending it.

Recommendation

Let players see the summary screen for ~2 seconds (or one tap) before Jessie appears. Sequence: show results → player taps "See what Jessie thinks" button (or it auto-fires after 2s with a dismiss option) → Jessie dialogue → Continue. The results screen can dim slightly behind the dialogue if desired. This ensures the player sees their reward first before receiving commentary on it.

Medium Both

Primary and secondary actions use identical button styling

Problem

"CONTINUE" (advance game) and "VIEW GLOBAL RANKINGS" (optional detour) use the same .snes-btn class. Players must read both to know which advances the game. On mobile, with fat-finger tapping, accidental "VIEW RANKINGS" taps pull players out of the flow.

Recommendation

Use the existing .snes-btn-yellow class for the primary action ("CONTINUE" or "ADVANCE TO NEXT TIER"). Secondary actions ("VIEW RANKINGS", "VIEW CAREER STATS") use standard .snes-btn. This is already the established pattern in the game — just apply it consistently on the summary screen. Consider placing secondary actions in a row above the primary CONTINUE button so it reads top-to-bottom as "options → confirm."

Low Mobile

Trophy images are too small to appreciate on mobile

Problem

Trophy size scales from 40px (T1) to 80px (T5) using inline styles. On mobile, a 40px or 48px pixel-art trophy is too small to see the detail. For a moment meant to feel like a reward, this is underwhelming.

Recommendation

Use a minimum of 80px on mobile and 96px on desktop for all trophy displays on the summary screen. The specific tier distinction (40px vs. 80px) isn't meaningful enough to justify the size difference — players want to see the trophy. The trophy case in Career Summary can use the tiered sizes since it's a collection view. But the moment-of-earn display should feel like a reveal, not a footnote.

Off-Season Screen offSeason.js

Season transition, respec, Jessie check-in, inventory reset.

High Both

Inventory is silently cleared — players don't see what they lost

Problem

The off-season screen clears the player's entire powerup inventory with a single line of text: "Your powerup inventory has been cleared for the new season." If a player spent 6 matches collecting a Legendary powerup they never got to use, it disappears without a ceremony. There's no list of what was lost and no chance to feel the loss/gain contrast.

Recommendation

Show a "SEASON COMPLETE — INVENTORY CLEARED" panel before the Respec button. List the cleared powerups in a small grid (icon + name, 4 per row). If the player had Legendary powerups, highlight them: "⭐ Lost: Jessie Did Her Homework (Legendary)". This creates emotional texture — the loss makes the next season's drops feel more valuable. Then a clear "I understand — Begin Respec" button proceeds.

Medium Both

Off-season doesn't preview the skill tree changes from the respec

Problem

The off-season confirms: "Root nodes kept. All other nodes refunded for X pts." But it doesn't show which nodes those are. Players must click into the Respec flow to see the resulting tree state. First-time off-season players may not realize their L2+ nodes are gone until they see the tree.

Recommendation

Show a simple text summary before the Respec button: "Keeping: MIND.1 (Mind Power), MYSTIC.1 (Mystical Power). Refunding: NPR, Blank Slate, Tweak Reality, Third Time's the Charm (+65 pts)." Exact node names, exact point count. Players can verify their understanding before committing. This also doubles as a helpful reminder of what they had.

Low Both

Jessie and player portraits have identical visual treatment — confusing side by side

Problem

On screens where both the player's HUD chip (top-left) and a Jessie dialogue panel appear, both use similar portrait frames and border styling. At a glance it's not immediately clear which is the player avatar and which is Jessie.

Recommendation

Give Jessie panels a distinct gold/amber border (border-color: var(--snes-yellow)) and a small "COACH JESSIE" label above the portrait. The player portrait uses the standard var(--snes-border) blue. This visual language differentiates advisor from player without changing the overall aesthetic.

Career Summary careerSummary.js

Lifetime stats, throw distribution, trophy case. Accessed from character select.

Medium Both

Throw distribution table conflates percentages and counts under ambiguous headers

Problem

The throw distribution shows "PLAYS" labeled columns that display percentage values (e.g., 33.3%), not play counts. A player who threw Rock 80 times out of 240 total throws sees "33.3%" which they might interpret as a win rate rather than a frequency. The column header doesn't match the value type.

Recommendation

Show both: PLAYS column shows the count (e.g., "80"), FREQ column shows percentage (e.g., "33%"), WIN% shows win rate. Or simplify to two columns: plays and win%. The key rule: if you show a percentage, label it with % in both the header and the cell. If you show a count, show a count. Don't mix without clear labeling.

Medium Both

No season-by-season breakdown — career stats are opaque totals

Problem

Career stats show lifetime totals only. A player in Season 7 who has improved dramatically since Season 1 has no way to see that arc. The lack of per-season data makes it hard to understand your own progress trajectory.

Recommendation

Add an ELO History chart using the seasonEloHistory data already stored in _trophies. A simple pixel-art sparkline (canvas, 8px segments per season) shows peak ELO per season across 10 seasons. This is already stored — it just needs a renderer. Even a text table of "Season 1: 1050 · Season 2: 1180 · Season 3: 1340…" is significantly better than nothing.

Low Both

"How to Play" link opens an external tab that may 404

Problem

The settings popup links to SRPS_how_to_play_v1_0.html in a new tab. If the file doesn't exist or was renamed, the tab opens to a blank or 404 page — a broken experience from a settings menu.

Recommendation

Either (A) inline a basic How to Play overlay within the game itself (a multi-page tap-through modal using the existing dialogue system), or (B) verify the file exists at boot with a fetch(url, {method: 'HEAD'}) check and disable the button if it 404s. Option A is better UX; Option B is a safety net. For v1.0, Option A is the right choice since the audience won't have seen Jessie tutorial beats yet.

Global Issues style.css · All Screens

Issues that span multiple screens or affect the entire game experience.

Critical Mobile

8px base font in "Press Start 2P" is at the lower edge of readability for body text

Problem

"Press Start 2P" is designed for display and UI labels, not running text. At 8px (the body default) on a 375px-wide phone, lines of descriptive text — skill descriptions, powerup effects, Jessie dialogue — require concentration to read. In poor lighting or for players with even mild visual impairment, this crosses from "retro" to "inaccessible." Skill effect descriptions in the detail panel at 7px or 6px are effectively decorative only.

Recommendation

Create a two-font system: "Press Start 2P" for UI labels, headers, button text, and game values (ELO, scores) — everywhere the pixel font is the aesthetic. A secondary sans-serif (system-ui or Inter) at 14px for all descriptive text: skill descriptions, powerup effect text, Jessie dialogue, tutorial beats, and how-to-play content. This is a common game design pattern — the pixel font does the visual work while a readable font handles information density. The switch won't break the SNES aesthetic if it's applied to body text only.

High Both

No loading or transition states between screens

Problem

Screen transitions are instant — innerHTML is replaced and event listeners are re-bound. On slower devices or with complex screens (match.js), there may be a brief flash of white or blank before content appears. This can look like a bug. More importantly, there's no sense of "moving" between screens.

Recommendation

Add a simple CSS fade transition: fade out (150ms) → swap screen content → fade in (150ms). Total 300ms, barely perceptible, eliminates blank flashes. Implement as a navigate(screen) wrapper in main.js that applies opacity: 0, waits, swaps, then applies opacity: 1. This is 10 lines of code and dramatically improves the feeling of navigation.

High Mobile

HUD chip (top-right) can overlap screen content without spacer on all screens

Problem

The HUD chip is position: fixed; top: 8px; right: 0, floating over all screens. The match screen has a .match-hud-spacer that pushes content down, but not all screens apply this. On screens without the spacer, the top-right corner of content can render under the chip — making character names, button labels, or stat values hidden behind the player widget.

Recommendation

Add a universal .hud-spacer { height: 52px; } as the first child of every .screen div. Or better: apply padding-top: 52px to the .screen class itself in CSS and remove individual spacers. This ensures the HUD never obscures content regardless of which screen is active. Test specifically on screens that currently start content at the very top (login, intro, tournament).

High Both

Modal / popup z-index competition creates layering conflicts

Problem

Three types of modals exist with different z-indexes: the scanline overlay (z-index: 9999), the HUD (z-index: 1000), and the powerup popup (z-index: 2000+). Settings modals use z-index: 2000 as well. With scanlines at 9999 drawing over everything, and popups at 2000, there's a large unused gap and potential for future overlapping layers as the game grows.

Recommendation

Establish a documented z-index scale in :root CSS variables: --z-hud: 100, --z-overlay: 200, --z-popup: 300, --z-scanlines: 400. All elements reference these variables rather than hardcoded integers. This makes the layer order legible and prevents accidental clipping as new UI elements are added. Scanlines should be the topmost layer since they're a post-process visual effect.

Medium Mobile

Touch targets below 44px on several interactive elements

Problem

Apple HIG and WCAG recommend minimum 44×44px touch targets. Several elements are smaller: skill node boxes in the tree (30–40px), powerup tray slots (variable), the 6px "SKIP" button on intro, and the tournament view-toggle buttons (font-size: 8px; padding: 6px 12px = approximately 30px tall). Mis-taps on the skill tree are especially painful given the purchase consequences.

Recommendation

For nodes that can't be visually larger, use the CSS padding trick with a larger transparent hit area: position: relative; &::after { content: ''; position: absolute; inset: -8px; }. This expands the tap target without changing visual size. Apply to: skill tree nodes (canvas targets → convert to div elements), small navigation buttons, and the intro skip button. Audit all buttons with a touch-target overlay tool in Chrome DevTools.

Medium Both

Identical modal component used for both powerup inspect and skill inspect — no distinction

Problem

The #pu-popup modal serves both powerup inspection (USE button) and skill inspection (status only, no action). The modal header and structure are nearly identical in both cases, making it easy to search for a USE button that isn't there (for skill inspects) or miss a USE button that is (for powerup inspects).

Recommendation

Differentiate the two with a clear header type indicator: POWERUP (gold border, USE button) vs SKILL (blue border, info only). The existing tier/tree badge system can handle this. Add a "PASSIVE SKILL — No activation required" note at the top of skill inspect popups. This resolves the confusion about whether action is possible.

Low Both

Scroll position is not preserved on screen re-renders

Problem

Screens re-render via innerHTML = replacement, which resets scroll position to the top. In the skill tree, if a player scrolls to see L4 nodes and then purchases one, the screen re-renders and scrolls back to the top — requiring them to scroll down again to see the updated state.

Recommendation

Capture scrollY (or the scroll container's scrollTop) before render and restore it after: const y = container.scrollTop; render(); container.scrollTop = y;. This one-liner prevents the jump. Apply to any screen where the user might be mid-scroll when a render is triggered (skill tree, match screen, tournament bracket).
